# Internationalization (i18n) — translation workflow

OpenMatch ships English as its source language and stubs out four
additional locales (`es`, `fr`, `de`, `ja`) so the .strings / .json
bundles exist in the project structure from day one. Stub locales
intentionally carry `???key???` as every value — we **do not** ship
machine translations. Accurate, native-speaker translations should
come from the community.

## iOS (`ios/OpenMatch/Resources/<lang>.lproj/Localizable.strings`)

### Source of truth

`en.lproj/Localizable.strings` is the master file. Every user-visible
string in SwiftUI views uses one of these idioms:

```swift
// LocalizedStringKey (preferred for static copy):
Text("swipe.empty_state.title")

// String(localized:) when you need a `String` rather than a `Text`:
TextField(String(localized: "welcome.email.placeholder"), text: $email)

// String(format: NSLocalizedString(...)) when you need to interpolate:
String(format: NSLocalizedString("match.subtitle",
                                 value: "You and %@",
                                 comment: "..."),
       card.displayName)
```

The matching backend error copy lives in `ErrorMessages.strings` and is
keyed by backend error code (see `backend/src/lib/error-codes.ts`).
Keep the two files separate so error-registry refactors don't churn
the general-copy bundle.

### Naming convention

`<feature>.<section>.<element>`

- **feature**: `onboarding`, `welcome`, `swipe`, `match`, `profile`,
  `chat`, `likes`, `settings`, `safety`, `common`.
- **section** (optional): `empty_state`, `action_row`, `toolbar`,
  `alert`, etc.
- **element**: `title`, `subtitle`, `body`, `button`, `label`, `hint`,
  `a11y_label`, `placeholder`, `confirm`.

Accessibility-specific copy gets the `a11y_label` / `a11y_hint`
suffix so it's easy to grep for.

### Format specifiers

Preserve them exactly when translating. Use positional forms
(`%1$@`, `%2$@`) when the target language wants to reorder arguments.

| specifier | type                           |
| --------- | ------------------------------ |
| `%@`      | Objective-C string             |
| `%lld`    | 64-bit integer                 |
| `%.1f`    | one-decimal float              |
| `%1$@`    | positional string (first arg)  |

### Date / number / distance formatting

**Never** compose these manually. Use the system formatters so the
locale picks the right pattern automatically:

```swift
// Distance (kilometers):
let m = Measurement(value: distanceKm, unit: UnitLength.kilometers)
let formatted = m.formatted(.measurement(width: .abbreviated))

// Date:
let when = message.sentAt.formatted(date: .abbreviated, time: .shortened)

// Number:
let count = matches.count.formatted(.number)
```

If you must use `String(format:)` (e.g. to compose two pieces of
copy), pull the format string itself from `Localizable.strings` so
the comma/decimal separators and ordering can be translated.

### Right-to-left (RTL)

SwiftUI's defaults handle most of RTL automatically:
- `.padding(.leading, …)` / `.padding(.trailing, …)` — flips with
  the writing direction. **Use these.**
- `.padding(.left, …)` / `.padding(.right, …)` — does **not** flip.
  Avoid these. The codebase has been swept for them; new code should
  only use `leading` / `trailing`.
- `HStack` lays out leading-to-trailing. Don't hard-code visual
  ordering with `Spacer()` + reversed children for cosmetic reasons —
  it'll look correct in RTL.

The handedness preference (`SettingsView` → action-button placement)
still uses `.right` / `.left` / `.center` because that's a user
preference about thumb-reach, not a writing-direction concern.

### Adding a new string

1. Pick a key following the naming convention above.
2. Add the key + English value to `en.lproj/Localizable.strings`.
3. Add the same key to **each** stub locale file with the value
   `"???<key>???"`. CI fails the build if a key is missing from any
   locale.
4. Reference the key in SwiftUI as shown above.

### Validating

```bash
# Generate the canonical key list from sources (informational):
find ios/OpenMatch -name '*.swift' | xargs genstrings -o /tmp/genstrings

# Diff the en.lproj keys against each stub locale (CI does this):
python3 scripts/i18n/check-locale-parity.py
```

## Admin (`admin/messages/<lang>.json`)

The admin dashboard uses static JSON message bundles. Most admin
pages are server components and the strings are static, so we don't
yet need a full `next-intl` bootstrap — a thin `getMessages(locale)`
helper reads the bundle once at module load. When dynamic per-user
locale switching becomes a requirement (it currently isn't — admins
operate the dashboard in English), we'll migrate to `next-intl` proper.

### Detecting locale

`admin/middleware.ts` parses the `Accept-Language` header and sets a
`x-om-locale` request header that server components read via
`headers()`. Fallback chain: explicit `?locale=` query param →
`Accept-Language` best match → `en`.

### Adding a string

1. Add the key + English value to `admin/messages/en.json`.
2. Add the same key with `"???<key>???"` to every stub locale file.
3. Read in a server component with `getMessage(key)`.

## Why stub translations?

Machine-translated dating-app copy reads wrong in every language we
checked. "Continue with email" lands as "Procéder à courriel" in
naive French — technically valid, deeply unidiomatic. We'd rather
ship the English bundle to non-English locales (which Apple's bundle
resolution falls back to automatically) than ship machine-translated
copy that signals "this app doesn't respect your language."

When a community contributor opens a PR translating a locale, that's
the moment we flip the locale from stub to shipped. The `???key???`
placeholder is the contract: anything still bearing that marker is
known-untranslated and the fallback to English is intentional.
